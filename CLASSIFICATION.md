# Класифікація Agent Skills

Ця політика визначає, де зберігати новий skill до того, як його текст або допоміжні файли потраплять у Git.

## 1. Public

Skill може бути загальнодоступним, якщо одночасно виконуються всі умови:

- методика корисна поза однією організацією або проєктом;
- приклади синтетичні, а назви організацій використані лише з дозволу або як явно ілюстративні;
- немає службових документів, персональних даних, секретів, облікових записів або приватних абсолютних шляхів;
- немає реальних внутрішніх схем доступу, мережі, інфраструктури, підрозділів чи розміщення ресурсів;
- немає процедур, публікація яких створює операційний або безпековий ризик;
- зовнішні матеріали мають зрозуміле походження та допустимі умови використання;
- skill залишається корисним без доступу до приватного контексту.

Public skills зберігаються в цьому репозиторії:

```text
agent-skills/skills/<skill-name>/
```

## 2. Service

Skill є службовим або внутрішнім, якщо містить хоча б один із таких елементів:

- реальні службові форми, коди, довідники, регламенти або схеми даних;
- інформацію про підрозділи, персонал, місця, маршрути, запаси, доступи чи оперативний стан;
- внутрішні адреси, порти, облікові записи, назви систем або топологію;
- процедури реагування, контролю чи обходу проблем, небезпечні при публікації;
- клієнтські або партнерські матеріали з обмеженим доступом;
- вимоги, походження чи дозвіл на публікацію яких не встановлено.

Такі skills не можна зберігати в цьому публічному репозиторії навіть у папці `service/`, у приватній гілці або в історії видаленого коміту. Для них потрібен окремий **приватний репозиторій**, наприклад:

```text
service-agent-skills/
├── skills/
├── profiles/
└── references/
```

## 3. Public core + private profile

Коли методика універсальна, але конкретне застосування службове, розділяйте її:

- **Public core:** загальний порядок роботи, доказові стандарти, безпечні межі, нейтральні шаблони й синтетичні приклади.
- **Private profile:** конкретні форми, поля, ролі, нормативні посилання, схеми даних, допустимі джерела та внутрішні правила.

Приклад:

```text
Public:  document-reconciliation
Private: unit-assets-reconciliation-profile
```

Публічне ядро має працювати самостійно. Воно не повинно розкривати існування, назви або структуру приватних ресурсів. Приватний профіль може посилатися на встановлене публічне ядро лише тоді, коли спосіб встановлення й версія однозначні; інакше він має бути самодостатнім.

## 4. Рішення перед створенням

Поставте п'ять запитань:

1. Чи може незнайома людина безпечно побачити всі файли skill?
2. Чи залишиться skill корисним після видалення назв, шляхів та внутрішніх деталей?
3. Чи є дозвіл на публікацію кожного реального прикладу й джерела?
4. Чи не допомагає skill відтворити внутрішню систему, доступ або операційну процедуру?
5. Чи немає сумніву щодо службового, персонального або ліцензійного статусу матеріалу?

Якщо хоча б одна відповідь негативна або невідома, класифікуйте skill як **Service**.

## 5. Переведення Service → Public

Публікація можлива лише після окремої санітизації:

1. створити нову чисту копію без приватної Git-історії;
2. замінити реальні дані синтетичними;
3. видалити внутрішні назви, шляхи, ідентифікатори та інфраструктурні деталі;
4. перевірити права на джерела й приклади;
5. виконати автоматичний пошук секретів і ручний review;
6. підтвердити, що сама процедура не є чутливою навіть після редагування даних;
7. лише після цього додати skill до `agent-skills` окремим перевіреним комітом.

Просте видалення чутливого файлу з останнього коміту недостатнє: він може залишитися в Git-історії.
